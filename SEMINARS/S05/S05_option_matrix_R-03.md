# S05 — R-03 Утечка PII / email через логи, ошибки и input (Info Disclosure)

## Контекст риска (из S04)

- **Risk-ID:** R-03 **Threat:** I (Info Disclosure)
- **DFD element/edge:** Edge/Node: Request, DTO, Logs, Errors
- **NFR link (ID):** NFR-006, NFR-009 -**L×I (1-5):** L=3, I=5, Score=15
- **Ограничения/предпосылки:** Backend (FastAPI), стандартные логгеры, централизованный storage логов, аудит и хранение по 30 дней, privacy требования по GDPR/152-ФЗ (PII), email и webhook используются для нотификаций, SLA по инцидентам — 72 часа.

---

## Критерии и шкалы (1-5)

**Польза (чем больше - тем лучше, ↑):**

- **Security impact (↑):** насколько альтернатива снижает риск (предотвращает/обнаруживает/сдерживает).
- **Blast radius reduction (↑):** насколько сужает возможный ущерб (только один тенант/аккаунт/фича вместо всего сервиса).

**Стоимость/сложность (чем меньше - тем лучше, ↓):**

- **Complexity (↓):** сложность внедрения (код/конфиг/политики).
- **Time-to-mitigate (↓):** сколько времени до эффекта (в днях/спринтах).
- **Dependencies (↓):** внешние/внутренние зависимости (команды, провайдеры, миграции).

> Оценка **1-5**: 1 - минимально / 5 - максимально. Для «стоимостных» критериев **меньше - лучше**.

**Итоговые метрики (подсказка):**

- **Benefit = Security impact + Blast radius reduction**
- **Cost = Complexity + Time-to-mitigate + Dependencies**
- **Net = Benefit − Cost** _(чем больше, тем привлекательнее)_

## Решение (ADR candidate)

**Chosen alternative:** Маскирование PII/email/webhook в логах (PII Masking in logs)
**Почему:** Быстро снижает риск, минимальные затраты времени/ресурсов, не требует глубокой перестройки логгирования.
**ADR candidate:** “Centralized PII Masking in Logging Layer”
**Связки:** Risk-ID R-03, NFR-ID NFR-006, NFR-009, DFD Edge/Node: Request, DTO, Logs

**Следующие шаги:**

1. Внедрить маскировщик PII/Email/Webhook в централизованный логгер.
2. Обновить существующие политики логирования (logging policy).
3. Протестировать masking на тестовых данных и edge-case (например, некорректный email).
4. Обновить документацию по правилам логирования и аудитам.
5. Внедрить алерт для случаев появления не-маскированного PII в логах.
