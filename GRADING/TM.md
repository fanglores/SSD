## 0) Мета

- **Проект:** учебный шаблон — REST API для управления токенами, уведомлений (email/webhook) и интеграций с внешними API. Пользователи: обычные пользователи/интеграторы и администраторы.
- **Версия (commit/date):** v1.0 / 2025-10-11
- **Кратко:** API-платформа принимает запросы с JWT/API-токенами, обрабатывает уведомления, хранит токены и аудит в БД; взаимодействует с внешними Vendor-x API.

## 1) Архитектура и границы доверия (TM1, S04)

- **Роли:**
  - `Клиент/Интегратор` (внешний актор)
  - `Администратор` (неявный, для аудита).
- **Активы:**

  - `API-токен` / `JWT` (учетные данные для доступа).
  - `ПДн (PII)`: `email`, `webhook_url`.
  - `Аудит-журналы` (доказательная база действий).
  - `База данных` (хранилище токенов, уведомлений, логов).
  - `Бизнес-логика` и `Доступность сервиса`.

- **Зоны доверия:**
  - **Интернет (`INTERNET`)**: Полностью недоверенная зона.
  - **Сервис: API/Контроллер (`APIENTRY`)**: Периметр, точка входа (DMZ). Принимает недоверенные данные.
  - **Сервис: Бизнес-логика (`SERVICE`)**: Внутренняя доверенная зона.
  - **Хранилище (`STORAGE`)**: Защищенная внутренняя зона, ядро системы.
  - **Внешний API (`EXTERNAL`)**: Внешняя, неконтролируемая зона. Доверие основано на API-контракте.
- **Context / DFD :**

  [Открыть DFD context (png)](../EVIDENCE/dfd-context.png)

- **Критичные интерфейсы / допущения:**
  - **Публичный API (`CLIENT` → `APIENTRY`)**: Основная точка атаки; все входящие данные по умолчанию не доверены и требуют валидации.
  - **Интеграция с внешним API (`SERVICE` ↔ `EXTAPI`)**: Интерфейс считается ненадежным; сервис должен быть устойчив к его сбоям (таймауты, Circuit Breaker).
  - **Доступ к хранилищу (`SERVICE` → `DB`)**: Разрешен только из компонента бизнес-логики.
  - **Допущение**: Секреты (API-токены) никогда не хранятся в открытом виде в БД (только хэши).
  - **Допущение**: Все критичные операции (создание/отзыв токенов) обязательно логируются в аудит-журнал.

## 3) Приоритизация и Top-5 (TM3, S04)

Top-5 по L×I (обоснование: экспозиция × критичность):

1.  **T01 Подмена личности** - L×I=16; высокая вероятность на публичном API; полный захват аккаунта.
2.  **T04 Утечка ПДн (PII)** - L×I=15; критический ущерб (I=5); частый вектор через логи и ошибки.
3.  **T07 MITM на внешнем API** - L×I=15; критический ущерб (I=5); компрометация через третью сторону.
4.  **T05 DoS-атака** - L×I=12; высокая вероятность на открытых эндпоинтах; простой сервиса.
5.  **T08 Кража токенов из БД** - L×I=10; критический ущерб (I=5); массовая компрометация при утечке.

## 4) Требования (S03) и ADR-решения (S05) под Top-5 (TM4)

### NFR-1. Аутентификация и авторизация (Риски: T01)

- **Rationale / Risk:** Митигация **T01 (Подмена личности)**. Гарантирует, что только легитимные пользователи с валидными токенами могут получить доступ к своим данным. (См. `NFR-003`).
- **AC (GWT):**
  - **Given** пользователь A с валидным токеном, **When** запрашивает `/api/tokens`, **Then** получает `200` и только свои данные.
  - **Given** просроченный/поддельный токен, **When** любой запрос к API, **Then** получает `401` и событие `auth.token_invalid` в аудите.
  - **Given** пользователь A пытается получить доступ к данным пользователя B, **When** запрос `/api/tokens/{TokenB}`, **Then** получает `404` без утечки информации.

### NFR-2. Защита от DoS (Rate Limiting) (Риски: T05)

- **Rationale / Risk:** Митигация **T05 (DoS-атака)**. Предотвращает истощение ресурсов из-за флуда запросами. (См. `NFR-002`).
- **AC (GWT):**
  - **Given** эндпоинты API, **When** количество запросов с одного токена превышает 1000 в час, **Then** сервис отвечает `429 Too Many Requests` с заголовком `Retry-After` и генерирует событие `rate_limit.hit` в логах.

### NFR-3. Защита от утечек ПДн (PII) (Риски: T04)

- **Rationale / Risk:** Митигация **T04 (Утечка ПДн)**. Гарантирует, что чувствительная информация не попадет в логи или ответы об ошибках. (См. `NFR-006`, `NFR-005`).
- **AC (GWT):**
  - **Given** запрос, который приводит к ошибке, **When** сервис генерирует ответ, **Then** ответ не содержит stack trace, а тело ошибки соответствует RFC7807.
  - **Given** любая операция с PII (email, webhook), **When** она логируется, **Then** чувствительные поля в логах маскируются (например, `user-***@domain.com`).

### NFR-4. Безопасное хранение секретов (Риски: T08)

- **Rationale / Risk:** Митигация **T08 (Кража токенов из БД)**. Предотвращает компрометацию всех токенов в случае утечки базы данных. (См. `NFR-001`).
- **AC (GWT):**
  - **Given** таблица `api_tokens` в базе данных, **When** любая запись сканируется, **Then** значение в колонке с токеном должно быть необратимым хэшем (например, `bcrypt` или `scrypt`).

### NFR-5. Безопасное взаимодействие с внешними API (Риски: T07)

- **Rationale / Risk:** Митигация **T07 (MITM на внешнем API)**. Гарантирует, что сервис общается с подлинным внешним API, а не с подставным. (Новый NFR, т.к. в реестре не было).
- **AC (GWT):**
  - **Given** сервис должен отправить запрос к внешнему API (`vendor-x`), **When** устанавливается HTTPS-соединение, **Then** сертификат сервера должен быть валидным и выданным доверенным центром сертификации (CA).

## Краткие ADR (выбранные / candidate):

#### ADR-001 - Короткий TTL JWT и механизм Refresh-токенов

- **Context (угрозы/NFR):** **T01** (Подмена личности), **NFR-003**; контур аутентификации на API Gateway.
- **Decision:** Установить короткий TTL (15 мин) для access-токенов в API Gateway. Внедрить механизм обновления через refresh-токены на отдельном эндпоинте `/api/auth/refresh`.
- **Trade-offs (кратко):** Усложнение логики на стороне клиента (должен поддерживать refresh), возможные UX-проблемы при ошибках обновления токена.
- **DoD (готовность):** Access-токен с TTL > 15 мин отклоняется с ошибкой `401`. Refresh-механизм работает согласно автотестам. Настроен алерт на аномалии в операциях обновления токенов.
- **Owner:** Security Team
- **Evidence (план):**
  - `EVIDENCE/dast-auth-YYYY-MM-DD.pdf#token-ttl-tests`
    - **Описание:** Отчет DAST-сканера (например, OWASP ZAP). Секция `token-ttl-tests` демонстрирует: 1) Запрос с токеном старше 15 минут получает `401 Unauthorized`. 2) Успешный вызов эндпоинта `/api/auth/refresh` с валидным refresh-токеном. 3) Получение новой пары access/refresh токенов в ответе.
  - `EVIDENCE/config-gateway-ttl.png`
    - **Описание:** Скриншот из файла конфигурации API Gateway или сервиса аутентификации, где явно установлены параметры `auth.access_token_ttl: 15m` и `auth.refresh_token_ttl: 7d`.

#### ADR-002 - Централизованное маскирование ПДн в логах

- **Context (угрозы/NFR):** **T04** (Утечка ПДн), **NFR-006**, **NFR-009**; слой логирования и обработки ошибок сервиса.
- **Decision:** Внедрить фильтр-маскировщик на уровне центрального логгера, который автоматически скрывает поля `email` и `webhook_url` перед записью лога в хранилище.
- **Trade-offs (кратко):** Усложнение отладки инцидентов, связанных с конкретными пользователями, так как их ПДн в логах будут скрыты.
- **DoD (готовность):** В логах отсутствуют ПДн в открытом виде (проверено скриптом). Автотесты на маскирование полей `email`/`webhook_url` проходят. Настроен алерт на случай просачивания не-маскированных ПДн.
- **Owner:** Security Team
- **Evidence (план):**
  - `EVIDENCE/log-masking-example.txt`
    - **Описание:** Фрагмент лога из production-like окружения. Демонстрирует, что в сообщении об ошибке поле `email` заменено на `user-***@domain.com`, а `webhook_url` на `https://***.corp.com/...`.
  - `EVIDENCE/scan-logs-pii-YYYY-MM-DD.log`
    - **Описание:** Результат работы скрипта, сканирующего хранилище логов за последние 24 часа по regex-шаблонам email и URL. Отчет показывает `PII_FOUND: 0`, подтверждая эффективность маскирования.
